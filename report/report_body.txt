1. Introduction and Scenario

For this assignment, I chose a food delivery system as my real-world scenario. I order food on apps like Swiggy and Zomato quite often, and I was curious about what happens on the server side when I press "Place order". A food delivery app also fits DevOps well. It has clear peak hours at lunch and dinner, menus and offers change almost every day, and if the app is down for even half an hour, restaurants lose orders and customers just switch to another app. So the team has to release changes often but still keep the system stable, which is the problem DevOps tries to solve.

I built a small version of this kind of app and called it QuickBite. It is an order API written in Python with Flask. The / endpoint returns basic information about the app, /health checks whether the database can be reached, /api/menu lists menu items from three sample restaurants (Spice Garden, Pune Biryani House, and Daily Dosa), and /api/orders lets a customer place an order or see existing orders. I kept the application simple on purpose, because the main focus is the DevOps side: how the app is built, tested, deployed, and monitored, and how the servers are configured with Ansible.

A real food delivery platform has customers who browse menus and place orders, restaurant partners who prepare the orders, delivery partners, and an operations team that keeps everything running. My version only implements the customer side, but the server layout is the same one a bigger app would start with.

QuickBite runs on three servers. web01 runs Nginx as a reverse proxy, app01 runs the Flask app under Gunicorn as a systemd service, and db01 runs PostgreSQL 14, which stores the menu and the orders. All three also run Prometheus node_exporter on port 9100. I did not have three virtual machines, so for the lab, I used three Ubuntu 22.04 Docker containers that run systemd and an SSH server. Ansible connects to them over SSH the same way it would connect to normal VMs, so the playbook would work on real servers without changes.

2. DevOps Lifecycle for QuickBite

I divided the lifecycle into eight stages: Plan, Code, Build, Test, Release, Deploy, Operate, and Monitor. The first four are mostly on the development side, and the last four are on the operations side. Figure 1 shows the stages with the tools I selected for each one. The dashed arrow from Monitor back to Plan is important because problems seen in production should become new work items, so the cycle keeps going.

2.1 Plan

For QuickBite, the backlog would be kept in Jira as user stories, for example "customer can place an order", "customer can track the delivery", and "add online payment". Each sprint picks a few of them. I think infrastructure work should be planned the same way. Adding a second app server before a festival sale should be a ticket like any other change.

2.2 Code

All code is kept in Git and pushed to GitHub. Every change is made in a feature branch and merged into main through a pull request after review. In my repository, the Ansible inventory, roles, playbook, and CI workflow sit next to the Python code, so the server configuration also has a history and goes through review. This is what infrastructure as code means in practice.

2.3 Build

Python has no compile step, so here the build means installing the dependencies from requirements.txt in a clean environment. I pinned the versions (Flask 3.0.3, Gunicorn 22.0.0, and psycopg2-binary 2.9.10) so the CI runner and the servers get the same packages. GitHub Actions does this on every push. Jenkins could do the same job, and later the app could be packaged as a Docker image, but I did not need that here.

2.4 Test

There are three types of checks. Unit tests in tests/test_app.py are run with pytest. They check that the index endpoint returns the app name and that /health returns 503 when the database is not reachable, which matters because the CI machine has no database. The automation code is checked with ansible-playbook --syntax-check and ansible-lint. For a bigger version, I would also add API tests in Postman and browser tests in Selenium.

2.5 Release

When all checks pass on main, the version is tagged in Git (for example, v1.0.x) and a GitHub Release is created. Staging can be deployed automatically, but for production I would keep a manual approval, because a broken release at dinner time directly affects orders.

2.6 Deploy

Deployment is done with the Ansible playbook site.yml, which uses four roles: common, database, app, and nginx. The same playbook is used for every environment, and only the inventory changes, so staging and production stay as similar as possible. It is one command and gives the same result every time, which is much safer than logging in to each server and typing commands by hand.

2.7 Operate

Here the app is serving traffic. Nginx accepts requests and passes them to Gunicorn, systemd keeps the QuickBite service running and restarts it on failure (Restart=on-failure), and PostgreSQL stores the data. I also used Ansible ad-hoc commands to check services on all servers at once, and the playbook to fix a configuration I broke on purpose (Section 8.6).

2.8 Monitor

Every server runs node_exporter, which exposes CPU, memory, disk, and network metrics on port 9100. In the full design, Prometheus scrapes these metrics, and Grafana shows them on dashboards. The /health endpoint tells whether the app can reach the database, and Nginx writes separate QuickBite access and error logs. In my lab, I installed node_exporter on all servers and checked that it returns metrics, but I did not set up the Prometheus and Grafana servers, as that was outside the scope of this assignment. Alerts and bugs go back into Jira, and the cycle starts again.

4. Architecture

Figure 2 shows the architecture that the playbook creates. It is a normal three-tier setup. A customer request first reaches Nginx on web01 port 80, which is mapped to 8088 on my machine, so I use http://127.0.0.1:8088 in the curl commands. Nginx forwards it to the upstream quickbite_app, which points to Gunicorn on app01, port 5000, and the Flask app connects to PostgreSQL on db01, port 5432, using psycopg2.

I kept the tiers on separate servers so that the app tier can be scaled by adding more app servers behind Nginx at peak hours, and so the database is never exposed to customers. The only network rule the playbook adds to pg_hba.conf is for the app servers to reach quickbite_db, with scram-sha-256 authentication.

The other part of the diagram is the management side. The Ansible control node is my Debian machine. Ansible reads the inventory and connects to each server over SSH as the user ansible with a key stored in ~/.ssh/quickbite/. That user has passwordless sudo, and become is enabled in ansible.cfg. One detail that took me some time to understand is that each server has two addresses in this lab. ansible_host (127.0.0.1 with a different port) is only used for SSH from the control node, while the servers talk to each other on their private Docker network address, which I keep in a variable called private_ip.

5. DevOps Workflow and CI/CD Pipeline

Figure 3 shows the workflow for a change going from a developer to production. The developer pushes a branch and opens a pull request. GitHub Actions runs ansible-lint, the syntax check, and pytest. If something fails, the developer fixes it. If everything passes, the change is merged into main and tagged. Then the playbook is run on the staging inventory, the verify play checks /health and /api/menu, and if staging is fine, the same playbook is run with the production inventory. Monitoring watches the new version, and issues go back to the developer.

The CI part is defined in .github/workflows/ci.yml, shown below.

The workflow runs on every push to main and on every pull request. It has two jobs, lint and test, which run in parallel on a fresh ubuntu-latest runner with Python 3.12. The lint job installs Ansible, ansible-lint, and the collections from requirements.yml (community.general and community.postgresql), then runs the syntax check and ansible-lint. The test job installs the app requirements and pytest, then runs the unit tests. A pull request should only be merged when both jobs pass.

The pipeline does not deploy by itself yet, because my lab servers are on my own machine and GitHub cannot reach them. I run the deploy step from the control node after the checks pass. In a real setup, I would add a third job that runs on tags and calls ansible-playbook with the production inventory from a self-hosted runner, with the SSH key stored as a GitHub secret.

6. Ansible Inventory and Configuration

The file ansible.cfg sets the defaults for the project. It points to the inventory and roles folders, turns off host key checking (the lab containers are rebuilt often, so their host keys can change), switches on sudo with become, and enables SSH pipelining to make runs faster.

6.1 Hosts and groups

The inventory is in INI format in inventory/hosts.ini. I made one group per tier and a parent group for the whole application.

There are three groups: webservers, appservers, and dbservers, with one host each. All three containers are on my machine, so they share ansible_host=127.0.0.1 with different ansible_port values (2221, 2222, 2223). web01 also has http_port_public=8088, which the verify play uses to call the app from outside. The group foodapp is made with :children, so it contains all three tier groups, and I can target the whole application with hosts: foodapp. [foodapp:vars] sets env_name=staging. For production, I would add a second inventory with the same groups, different hosts, and env_name=production.

6.2 Group variables and host variables

I kept most variables in group_vars and host_vars because YAML is easier to read. group_vars/all.yml applies to every host and has the SSH user and key, the common packages, the ports of each tier, and the database details. The database values are here and not under dbservers because both the app and database roles need them.

Each tier group has its own small file, and each host has a file in host_vars:

The host variables show how precedence works. gunicorn_workers is 2 in group_vars/appservers.yml but 3 in host_vars/app01.yml, and postgres_max_connections is 100 for the group and 150 for db01. Host variables win over group variables, which I confirmed with ansible-inventory --host app01 --yaml (Figure 4). Each host also has a server_role text that the common role prints in the login banner.

private_ip is filled from the gathered facts, so I never type private IP addresses. The Nginx upstream and the pg_hba.conf rules loop over groups['appservers'] and read the private_ip of each host. So adding a second app server only needs one new line under [appservers]. On the next run, Nginx balances between both app servers, and PostgreSQL accepts the new one.

7. Ansible Playbook and Roles

7.1 Main playbook (site.yml)

site.yml is the main playbook. It is short because all the real work is inside the roles. It has five plays, and each play targets one group.

The order of the plays matters. The common role runs first on all hosts. The database comes before the app, because when Gunicorn loads the app, it creates the tables and inserts the menu, so the database must already exist. Nginx comes after the app, and the last play verifies the whole chain. It runs the uri module from the control node (delegate_to: localhost) and calls /health and /api/menu through Nginx like a customer would, retrying up to five times because Gunicorn may take a moment to start. Each role has a tag, so one part can be run alone, for example with --tags nginx,verify.

7.2 Roles

All four roles use the standard layout (tasks, handlers, templates, files, defaults). Values a user may want to change are in defaults/main.yml or the inventory, not inside tasks, so a role like nginx or database can be reused in another project by only changing variables.

The common role updates the apt cache (cache_valid_time: 3600, so not on every run), installs the common packages (including prometheus-node-exporter), sets the timezone to Asia/Kolkata, starts node_exporter, and writes a login banner from motd.j2, which warns that the server is managed by Ansible.

The database role installs PostgreSQL, edits postgresql.conf with lineinfile (listen address, port, and max_connections), adds a pg_hba rule for every app server, and creates the database user and database with the community.postgresql modules. This part was the most interesting for me:

7.3 Handlers, templates, and idempotency

Each role that manages a service has handlers: "Reload systemd" and "Restart quickbite" in the app role, "Restart postgresql" in the database role, and "Reload nginx" in the nginx role. Tasks that change a config file notify them, so a service is restarted only when its configuration really changes. For Nginx, I used reload instead of restart so open connections are not dropped. Jinja2 templates are used for the Nginx site, the app environment file, the systemd unit, and the banner, and all values in them come from the inventory, so there are no hard-coded IPs or passwords in the roles.

I tried to make the playbook fully idempotent, meaning a second run changes nothing if the servers are already correct. Modules like apt, user, file, template, and service describe a state and not an action, so they are idempotent already. The only command task is nginx -t, which only checks the config, so I marked it changed_when: false. I also used full module names (for example, ansible.builtin.apt) and named every task, as the ansible-lint production profile expects.

Finally, I wanted to show why configuration management is useful after the first deployment. I removed the QuickBite site from Nginx by hand with an ad-hoc command, like a wrong manual change on a server, and then ran only the nginx and verify parts with --tags nginx,verify (Figure 13).

9. Challenges Faced and Solutions

The first issue was networking. At first, I tried to reach the containers directly on their Docker bridge IP addresses, but because of the network and firewall setup on my host, this was not reliable. So I mapped the SSH port of each container to a port on localhost (2221, 2222, 2223) and port 80 of web01 to 8088. That fixed SSH but created a second problem. Every host now had ansible_host=127.0.0.1, which I could not use in the Nginx upstream or pg_hba.conf, because inside a container 127.0.0.1 is the container itself. I solved it with the private_ip variable taken from facts, so SSH uses ansible_host and the servers use private_ip.

The second issue was the PostgreSQL driver. The normal psycopg2 package from pip is built from source, so the server needs a compiler and the PostgreSQL development headers. I did not want build tools on the app server, so I used psycopg2-binary pinned to 2.9.10. The community.postgresql modules also need psycopg2 on the database server, and there I installed the Ubuntu package python3-psycopg2 with apt instead.

The third point is the database password, which is in plain text in group_vars/all.yml. I left it like that only because this is a lab, with a comment in the file, and used no_log: true on the task that sets it. In a real project, I would encrypt it with Ansible Vault (ansible-vault encrypt_string or a separate vault file) and run the playbook with --ask-vault-pass, with the vault password stored as a GitHub secret for CI.

I also saw two warnings that did not cause failures. One is a deprecation warning about facts as top-level ansible_ variables, which points to my private_ip line and can be fixed by using ansible_facts['default_ipv4']['address']. The other is a remote_tmp warning on db01, for example, when a task uses become_user: postgres. I plan to clean up both in the next version.

10. Conclusion

In this assignment, I took a food delivery app as a real-world scenario, planned its full DevOps lifecycle, identified the development, testing, deployment, and monitoring stages, and designed a CI/CD workflow, part of which already runs in GitHub Actions. I prepared an inventory with tier groups, a parent group, and both group and host variables, and wrote a playbook with four reusable roles that sets up PostgreSQL, the Flask app with Gunicorn, and Nginx on three servers with one command.

The playbook passed ansible-lint with the production profile, ran without failures, gave changed=0 on the second run, and fixed a manual change by itself. What I learned most is that writing the playbook was only half the job. The other half was making it safe to run again and again, which is what makes a team trust automation. Next, I would add Ansible Vault, a production inventory, an automatic deploy job, and real Prometheus and Grafana servers.
